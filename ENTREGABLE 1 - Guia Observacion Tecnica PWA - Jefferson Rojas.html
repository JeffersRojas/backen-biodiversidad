1. Estructura del Proyecto

El proyecto BioColombia implementa una arquitectura distribuida de tres capas: un frontend PWA (HTML/CSS/JS puro sin frameworks, optimizado para campo y celular), un backend Spring Boot 3 hexagonal (Puertos y Adaptadores), y MongoDB como base de datos persistente. Adicionalmente hay una capa offline nativa dentro del navegador (IndexedDB + Service Worker) que garantiza funcionamiento sin red.

→
2. Evento INSTALL
→
3. skipWaiting()
→
4. Evento ACTIVATE
→
5. clients.claim()
→
6. FETCH / SYNC / PeriodicSync

📍 Registro desde app.js (post-FCP)

El registro del Service Worker se difiere hasta después del primer pintado de contenido (First Contentful Paint), dentro de _initAsync() ejecutado por requestIdleCallback. Esto evita bloquear LCP/FCP (recomendación Lighthouse).

async registerServiceWorker() {
  if (!('serviceWorker' in navigator)) return;
  try {
    const reg = await navigator.serviceWorker.register('./sw.js');
    reg.addEventListener('updatefound', () => { /* ... toast nueva versión ... */ });
    if (reg.waiting) reg.waiting.postMessage({type:'SKIP_WAITING'});
  } catch(e) { console.warn('SW falló', e); }
}

🟢 Evento INSTALL

Abre la caché biocolombia-appshell-v1 y pre-carga los 11 archivos del App Shell. Después llama self.skipWaiting() para activarse inmediatamente.

self.addEventListener('install', (e) => {
  e.waitUntil(
    caches.open(CACHE_APP_SHELL)
      .then(c => c.addAll(APP_SHELL))
      .then(() => self.skipWaiting())
  );
});

🔄 Evento ACTIVATE

Borra cachés antiguas (versionadas con -v1) y reclama todas las pestañas abiertas con self.clients.claim().

caches.keys().then(keys =>
  Promise.all(keys
    .filter(k => k !== CACHE_APP_SHELL && k !== CACHE_DYNAMIC)
    .map(k => caches.delete(k)))
).then(() => self.clients.claim())

🔔 Eventos adicionales (Background Sync)

El Service Worker escucha dos eventos extra del ciclo de vida de sincronización:

sync · tag sync-avistamientos

Registrado en SyncManager si el navegador soporta Background Sync. Cuando Chrome detecta que volvió la red, dispara el evento y el SW envía un mensaje BACKGROUND_SYNC_TRIGGER a todos los clientes (pestañas) para que ejecuten la lógica de envío por lotes (10 registros) usando el token JWT del usuario en IndexedDB.

periodicsync · tag periodic-sync-data (opcional)

Solo disponible en Chrome Android instalado (PWA standalone). Requiere permiso del usuario y origin trial. Está preparado como mejora futura pero no se usa por defecto; el mecanismo robusto es SyncManager foreground + sync.

Se usan tres estrategias diferenciadas según el tipo de recurso (recomendación Google PWA docs), sobre dos caché versionadas distintas:

💿 Cachés versionadas

A

B
biocolombia-dynamic-v1
Recursos dinámicos (imágenes, fotos, HTML navegado). Aplicado con Cache-First.

// Solo interceptamos GET.
// El otro (POST auth/avistamientos/batch) pasa a red
// y falla 503 JSON si offline.
if (req.method !== 'GET') return;

→ fallback offline.html		 Navegaciones HTML (req.destination === 'document'), URLs terminadas en .html, raíz / Siempre intentar HTML actualizado. Si no hay red → mostrar offline.html standalone. Asegura que la app cargue incluso sin WiFi la primera vez después de instalada.
Stale-While-Revalidate App Shell core: index.html, styles.css, app.js, api.js, router.js, db.js, sync.js, imageCompress.js, manifest.json, offline.html, ./ Mostrar inmediatamente la versión cacheada (0 ms), y en paralelo descargar la versión nueva para la siguiente visita. Óptimo para UX instantánea sin sacrificar actualizaciones.
Cache First
→ fallthrough cache dinámico		 Imágenes (fotos avistamientos), estilos adicionales, scripts de terceros, recursos estáticos no-App-Shell Las fotos no cambian nunca. Ahorrar ancho de banda rural y 4G saturado en zonas rurales colombianas.

5. Estrategia de Actualización — skipWaiting y clients.claim

Por defecto un Service Worker nuevo se queda en estado waiting hasta que el usuario cierre TODAS las pestañas abiertas. Para biólogos de campo que nunca cierran la app (solo minimizan), esto causaría que nunca reciban actualizaciones. Por eso se aplica una estrategia agresiva de actualización inmediata:

⚡ self.skipWaiting()

Ubicado en el evento INSTALL (línea 21) y también accesible manualmente por postMessage:

// INSTALL - Activa inmediatamente, no espera cierre de pestañas
self.addEventListener('install', e => {
  e.waitUntil(/* cache.addAll */
    .then(() => self.skipWaiting()));
});

// Mensaje desde UI - botón "Actualizar ahora"
self.addEventListener('message', e => {
  if (e.data?.type === 'SKIP_WAITING') self.skipWaiting();
});

⚠️ Trade-off

Actualización inmediata puede causar que JS viejo pida recursos nuevos en mitad de una sesión. Se mitiga porque todos los recursos están en caché SWR (par/impar versionado) y porque el App Shell carga todo de una vez en la navegación inicial.

👥 self.clients.claim()

Ubicado en el evento ACTIVATE (línea 32). Hace que el SW recién activado empiece a interceptar peticiones de pestañas abiertas INMEDIATAMENTE, sin esperar a que el usuario recargue.

self.addEventListener('activate', e => {
  e.waitUntil(
    caches.keys().then(keys =>
      Promise.all(keys.filter(k =>
        k !== CACHE_APP_SHELL && k !== CACHE_DYNAMIC
      ).map(k => caches.delete(k)))
    ).then(() => self.clients.claim())
  );
});

🤝 Efecto combinado skipWaiting + claim

El navegador detecta un cambio en sw.js → instala nuevo → salta waiting → activa → reclama clientes. El usuario ve el toast "Hay una nueva versión" en app.js (reg.addEventListener('updatefound', ...)) y si pulsa "Actualizar" se hace postMessage + reload. Pero aunque no haga nada, ya se activa en background.

🔄 ¿Cómo se versionan los cambios? La actualización se orquesta cambiando el número de versión en el nombre de las cachés: pasar biocolombia-appshell-v1 a -v2 y el ACTIVATE limpia la v1 automáticamente. No hay Workbox; estrategia manual para transparencia total y facilitar debugging en campo.

🚀 Propuestas de mejora para siguiente entrega

  • Pasar íconos SVG inline de manifest → archivos PNG 192/512 reales. Algunos navegadores antiguos no renderizan data:image/svg en launcher Android.
  • Añadir screenshots[] al manifest (campo vacío ahora). Mejora el diálogo de instalación Chrome Android con una previsualización de la app.
  • Añadir Service Worker update banner visible: en app.js el evento updatefound existe pero no muestra banner UI, solo console.log.
  • Desplegar HTTPS (Netlify/Vercel frontend + Railway/Render backend SSL) para quitar alerta Lighthouse HTTPS.
  • Añadir aria-live="polite" al contenedor de Toast y Dashboard stats para lectores de pantalla NVDA/JAWS.
  • Optimizar LCP con preload de estilos: añadir <link rel="preload" href="css/styles.css" as="style">.
  • Usar Workbox v7 para reducir líneas de sw.js y obtener estrategias con expiry plugins y range requests para fotos grandes.
